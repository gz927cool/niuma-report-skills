# 通俗版分析报告写作

把技术分析结果改写成非技术读者能独立读懂的报告。这个技能的价值在于避免一类反复出现的返工：写的人觉得"已经说清楚了"，读者却看不懂、被误导、或觉得不专业。

## 两个定位（决定全文口吻）

1. **报告以使用者的名义发给第三方**。读者是使用者的领导、客户、合作方——文中不得出现任何"作者自述"痕迹：没有"（诚实的局限，先承认）"式的章节标注，没有"不美化""实打实"式的表态句，没有第一人称的写作过程叙述。全部用第三人称陈述事实与数字。
2. **报告必须独立可读**。读者手边没有技术版、没有代码仓库、没有上下文。拿到手的这一份文档是唯一信息源。

读者画像：不懂统计和代码的业务方。他们擅长业务逻辑，缺的只是术语和口径翻译。

## 动笔前确认三件事

1. 输入在哪：技术版报告路径，或对话中已给出的结果数字
2. 读者是谁：决定概念解释深度（管理层要结论+风险，客户要效果+边界）
3. 有无篇幅要求：**可以压缩方法细节，不可以牺牲结论与证据链的完整**——"简短"是压缩表述，不是砍掉关键环节

## 六条核心规则

### 1. 独立可读

不引用：文件路径、代码文件名、变量名、表名、内部代号（模型代号、需求编号、偏差编号如 D5/R14）。
Why：读者无法访问仓库，任何外部引用都是死链；内部代号迫使他们猜测指代。

### 2. 完整覆盖重要环节

技术版中的方法关键步骤必须以正式章节呈现，不能只在"发现"里顺带一提，更不能漏。典型的必写环节：
- 候选方案的对比与选择（比了哪些方案、在什么数据上比、按什么规则选定）
- 单个方案与组合/融合方案的分别成绩（若验收口径要求两者都报）
- 检验方式（怎么保证成绩是真的，如数据切分、防偷看机制）
Why：读者依据报告做判断。漏掉"我们比过哪些方案"，他们会高估单一结论的可信度；漏掉"怎么防作弊"，他们会低估。
注意：完整性指**结论与证据链**完整；技术细节可以通俗化压缩。

### 3. 数字诚实（最重要的一条）

- **不软化**：50% 不能写成"差一点没过"。差多少个百分点就写多少，附统计显著性就下结论。
- **比例类指标（准确率/命中率/判对率/正确率）必须附朴素基线对照**：给出"最笨规则"（如"一律猜最常见类""一律看涨"）在同口径下的成绩，说明净增量。单边行情、不均衡样本里，裸比例会被基线明显抬高。
- **同一数字全文口径一致，且先出现再引用**：结论段引用的每个数字，正文某节必须先完整出现过。
- **负结果照写**：没起作用的因子、没通过的检验、失效的方案，与正面结果同权重呈现。
- **机制写到"数是怎么算出来的"**：核心方法不能停在结论，要给步骤+例子，让
  读者能复述"这个数从哪来"。对话里讲明白了但文档没写的，回填进文档——读者
  没看懂，责任在文档不在读者。
- **交付稿的缺口表述（条件性：报告用于对外交付/合同时；面向内部读者时仍按上一条负结果照写、缺口直陈。场景以用户声明的用途为准，判不准时问一句）**：结果类负结果仍如实报数、不软化；"未实现/未接线"类范围缺口不写认错式清单，用正面框架带过（"同时输出，提供综合参考""留作标定项""可经配置接入"）。底线：绝不把没做的写成已做。
Why：读者无法自行核数。软化一个数字、漏掉一个基线，报告就从"信息"变成"立场"。

### 4. 通俗 ≠ 隐喻

用直述："先进行了基线对比"，不用"先比了一场武"。
**禁止贯穿全文的叙事框架**——考试/考场/考卷/小抄/帮手/同桌/比武这类把整个流程套进一个故事的比喻体系。市场与业务的常用语（横盘、利好、动量、基线等）可保留。
Why：隐喻对懂行的人是噪音，对不懂的人是二次翻译负担；且叙事框架会把读者的注意力从数字引向故事。

### 5. 中立书面口吻

通俗的实现手段是"**每个术语首次出现时给一句白话解释**"，不是口语化语气词。检查项：
- 无作者自述式标注（"（诚实的局限）""（先承认，再对照）"）
- 无表态句（"不美化""实打实""较真地说"）
- 无口语叙事词（"一句话：""说白了就是""数字好看"）
Why：这份文档以使用者署名发出，是正式文书，不是博客。

### 6. 概念前置

正文之前用最少的概念块（通常 2-4 个）让零基础读者武装起来，表格最清晰。典型三件套：
1. 这件事在预测/衡量什么（一句白话）
2. 用什么判断好坏（每个指标=通俗理解+及格线；这里"及格线"指朴素基线/随机水平等对照锚点，帮读者建立预期，不是验收判定）
3. 谁跟谁比（模型/方案/基线各是什么）
Why：读者中途遇到指标不会回头翻解释；概念块也是后文所有数字的锚点。

## 推荐结构

1. **摘要**：一段话——做了什么、关键结果（含最重要的负面结果）、最重要的限制
2. **基本概念**：2-4 个，白话+及格线（表格）
3. **做了什么/改了什么**：与旧做法的差异，逐条直述（业务层面的做法/口径变化，不是实现史对照）
4. **方法关键环节**：正式章节呈现（候选方案对比、防作弊机制等）
5. **结果**：验收口径总表；单个方案与组合方案的成绩都报（若适用）
6. **关键指标深度分析**：分场景/分时段拆解，一律附基线对照表
7. **其他发现**：含负结果
8. **局限性**：中性标题就叫"局限性"，逐条陈述
9. **改进建议**：按优先级

## 措辞对照（真实修正案例）

| 错误写法 | 正确写法 |
|---|---|
| 方向准确率"差一点"没过（实际 50%） | 50%，与随机猜测无显著差别（p=…），距及格线差 10 个百分点 |
| 正式评估前先比了一场武 | 正式评估前先做了候选方案的基线对比 |
| 事件期 69%~91% 是真实能力 | 对照"一直看涨"基线：一段完全持平、一段仅多对 1 天，不构成超越朴素规则的能力 |
| ## 能信多少（诚实的局限） | ## 局限性 |
| 两个帮手同桌一起做题、互相校对 | 两部分联合训练、交替修正残差 |
| 但 50% 就是 50%，不美化 | （删除——直接陈述数字与检验结果） |
| 模型里的 f1 部分得分 55.7% | 事件驱动部分得分 55.7%（首次出现时定义这个称呼） |

## 格式基线

- 一段一行软换行（表格/标题/图片独立行），不按固定宽度硬换行。
- 章节标题干净（不带冒号式评注后缀）；纯说明性文字不单设小节标题。

## 交付前自检清单

- [ ] 拿掉技术版后，一个不懂技术的读者能否独立读懂全文？
- [ ] 技术版的每个重要方法环节都有正式章节（而非顺带一提）？
- [ ] 每个比例类指标是否都附了基线/对照？
- [ ] 有无软化词（差一点/略逊/接近达标/勉强）？
- [ ] 有无叙事隐喻残留（比武/考场/帮手/小抄…）？
- [ ] 有无作者自述标注或表态句（诚实的/先承认/不美化/实打实）？
- [ ] 有无路径、文件名、变量名、内部代号？
- [ ] 结论段引用的每个数字，正文是否先完整出现过？口径是否一致？
- [ ] 摘要里是否包含了最重要的负面结果与限制？
- [ ] 一段一行软换行？标题干净（无评注后缀、无说明性小节）？
- [ ] 通俗版与技术版范围口径一致（对通俗版的收窄同步施加于技术版）？
