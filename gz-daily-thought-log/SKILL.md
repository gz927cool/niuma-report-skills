# 工作思路日志（gz-daily-thought-log）

把一段时期的工作整理成**非正式的思路汇报**。核心价值不是记录"做了什么"，而是还原"怎么想的"：问题如何一个接一个被逼出来、设想如何提出又如何被证据否定、用户在哪一步想通了什么。

## 产出

一份 markdown 日志，默认写入 `docs/work-log/YYYY-MM-DD-思路日志.md`（用户指定路径则从之；不要与同日 OA 工作日志 `YYYY-MM-DD-工作日志.md` 同名，避免相互覆盖），正文一段一行软换行（不硬换行）。
主线必须是**问题链**，不是任务清单。

## 流程

### 第 1 步：确定材料范围

1. 用 `git log --since` 和 `git diff --stat` 摸清当天提交与未提交变更，作为产物背景；
2. 列出 `.specstory/history/` 下相关会话文件。**注意文件名时间戳是 UTC，本地时间 = UTC + 8**；一场会话可能跨本地日期（昨天深夜开始、今天上午还在写），按内容发生时间归属，必要时看文件 mtime；
3. 用户点名排除的会话必须排除。**陷阱**：同一时间戳前缀可能有多个兄弟文件（如 `X.md` 与 `X-后缀.md`），它们常是同一场会话被拆分——读一下开头确认是否属于被排除的那场，是则一并排除；
4. 被排除会话产出的代码（用文件 mtime + 会话记录里的编辑动作核对归属）不要写进总结；
5. 当天没有会话记录时，退化到只基于 git log 写。

### 第 2 步：分派子智能体读会话，提取"用户本人的思路"

会话文件动辄几千行，主对话直接读会淹没上下文；而且"以用户视角重读"和"以分析视角重读"是两回事。每场会话派一个只读子智能体（Explore 类型），提示词按下面模板（已验证有效）：

```
你在读一份 Claude Code 会话记录（SpecStory 格式的 markdown）。
格式：用户消息以 `_**User (时间戳)**_` 开头；助手消息以 `_**Agent (...)**_` 开头；
`<tool-use>` 块是工具调用输出，`<think>` 块是助手思考，都跳过不细读。
文件较大，必须用 Read 的 offset/limit 分段读（每段约 1000 行），读完全文。

任务：提取【用户本人】的工作思路演进（不是助手的分析内容）。输出：
1. 按时间顺序列出用户每条消息的要义（关键原话保留引号）；
2. 每条消息背后用户想解决/想知道什么（一句话推断动机）；
3. 用户的假设与关注点如何一步步演进（先问了什么、看到什么结果后转向什么）；
4. 用户主动做出的决策或转向（换口径、换方案、指定数据源等）；
5. 用户的困惑或不满意之处（哪里没想通、哪里要求重做）。
用紧凑中文分点输出，带本地时间（=UTC+8）。不要复述助手的技术分析，
除非一句话上下文需要。
```

会话很短（几百行以内）时可以自己读，但提取视角不变。

### 第 3 步：综合成问题链

拿子智能体提取的思路轨迹当骨架组织报告：

- 主线 = 问题的演进：**每个问题是被上一个结果逼出来的**。写出因果（"看到日频相关只有 0.041 很失望 → 判断是噪声淹没信号 → 主动换口径 → 相关跳到 0.376 → 才提出改目标的设想"），不要写成"分三步进行"的计划式叙述；
- 用户提出设想 → 被否定 → 换角度再试 → 再被否定 → 想通的退让路径要原样保留（可以直白地写"我是分三步被说服的"），这是思路日志最值钱的部分；
- 关键发现要写**发现过程**（用户哪次主动换口径换出来的），不能当现成数字引用。

### 第 4 步：写入文件并自检

风格规则见下节。写完前过一遍自检清单：

- [ ] 主线是问题链吗？还是写成了任务清单/分析报告结构？
- [ ] 关键发现写出来路了吗？
- [ ] 通篇没有文件名、脚本名、课程/工具名等实现细节？
- [ ] 没有"方法论沉淀"式的自我评价章节？
- [ ] 数字都在，且每个旁边有一句大白话含义？
- [ ] 第一人称，无 AI/助手交互痕迹？

## 风格规则（每条都来自真实反馈，不是随口的规矩）

1. **非正式、第一人称**。这是给自己或技术同事看的思路汇报，不是邀功报告——用"我判断""我很失望""我没想通，要求通俗解释"这样的口吻。
2. **通俗，但信息不缩水**。核心问题直接陈述（写"尝试分析预测日频XX价格的可行性，判断政策/情绪类因子能提供多少信息"，不写"信号活在哪个时间尺度上"这类文艺腔）；术语就地翻译（单位根检验 → "价格对数是否必须差分才能用"）；每个数字配一句大白话（48% → "和抛硬币一样"）。通俗 ≠ 删数字：结论性数字全部保留。
3. **禁止出现**：文件名/脚本名（如 xxx.ipynb、xxx.py）、"Kaggle 课程式"这类学习来源标签、会话文件/聊天记录路径、"方法论沉淀/经验总结"式章节、对 AI 或工具交互的描述。这些对思路汇报毫无价值。
4. **结尾停在结论**。不加展望、不加自我评价、不总结"学到了什么"。

## 与 gz-daily-work-log 的边界

| | 本技能 | gz-daily-work-log |
|---|---|---|
| 受众 | 自己 / 技术同事 | 领导（OA 填报） |
| 语言 | 通俗 + 技术结论和数字保留 | 业务语言，去技术细节 |
| 主线 | 问题演进链、设想与否定过程 | 问题→解决→效果 |
| 依据 | 会话记录里的用户思路轨迹 | git 提交 + 对话补全意图 |

用户请求两者都沾边时，先问一句受众是谁，不要猜。
