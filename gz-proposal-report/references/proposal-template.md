# 提案标准结构模板

面向决策层的技术提案，五段递进。每段写什么、要点、示例。读者顺着读完正好走完"判断要不要做"的完整逻辑。

## 一、需求与背景（为什么）

**目的**：让领导理解"为什么要做这个"。

包含：
- **用户诉求**：用户典型问句 + 真实诉求 + 当前能给 + 还差什么（表格直观）
- **具体缺口**：当前系统做不到什么（2-3 条，每条带证据/现象）
- **本质差异**（关键）：新工作与既有工作的本质差异（表格对比），论证"为什么独立做、不能在既有产品加功能"

要点：
- 痛点要真实、具体（有现象/证据），不空泛
- 本质差异是"为什么独立做"的根本论证，比诉求深一层
- 用建设性叙事（延伸/拔高），不贬低既有工作

## 二、目标（做成什么）

**目的**：让领导看到"做成之后是什么样"。

包含：
- **能力定位**：新工作与既有工作的关系（建立在...之上、是其上的新场景）—— 用图（mermaid）展示层次关系
- **业务用户得到什么**：具体的能力清单（如结构化结论、图表、洞察、可信度）

要点：
- 用"延伸/拔高"叙事，不贬低既有工作
- "得到什么"要具体（用户能拿到什么），不抽象
- 与既有产品的协同（复用什么、新增什么）

## 三、方案路线（怎么做）

**目的**：让领导看懂"怎么搭、怎么走"，且看到具体交付什么。

包含（3 个层次）：
- **设计原则**（2-3 条思路）：如"计算归代码""分层""两阶段"——设计理念
- **主体路线**：架构图（mermaid + subgraph）+ 一次完整流程（步骤）——让领导看懂骨架
- **核心模块与范围**：五个左右具名模块 + v1 做/不做边界——落地锚点

要点：
- 这是"面向领导但不空泛"的核心——给架构图（骨架）+ 模块清单（锚点），不陷代码细节
- 讨论过的每个重点都要在这段有落点（沙箱/skills/分流/呈现等不能漏）
- 章节内职责分明：原则/架构/范围各管一段，不重复

## 四、规划（分几期）

**目的**：让领导看到"分几步走、每步交付什么"。

包含：
- **v1**：最小闭环（目标 + 关键交付 + 里程碑：用户第一次独立完成 X）
- **v2**：能力深化 + 质量闭环
- **v3**：规模化 + 资产化

要点：
- v1 要具体（交付什么、里程碑是什么），不贪多
- 留 v2/v3 的扩展空间
- v1 聚焦最小闭环，避免范围蔓延

## 五、可行性（能不能成）

**目的**：让领导判断"这事做得成、风险可控、投入合理"。

包含：
- **时机**（为什么现在做）：底座成熟、选型收敛、业界验证、诉求明确、不做的代价
- **风险与对策**（表格）：每个风险有对策，最高风险标清
- **资源需求**：需要什么（前端/环境/数据/配合），投入可控

要点：
- 可行性要诚实（风险不回避），但每条风险都要有对策
- 资源需求要具体（领导要知道批什么）
- 强调"站在成熟底座上、低风险可行"

---

## 通用要点

- **图用 mermaid**（+ subgraph 分组），不用 ASCII
- **章节职责分明**：五段各管"为什么/做什么/怎么做/分几期/能不能成"，不重复
- **统一命名**：同一个概念全文同一个名字
- **避免技术细节**：无 file:line、schema、协议字段、代码结构
- **抽象能力配具体例子**：写"输出洞察"要给具体洞察例子，不空说

## 控制篇幅

提案不宜过长（领导时间有限）。目标：领导 5-10 分钟能读完核心。五段各占合理比例，方案路线（三）最重（骨架+锚点都在这），其余精炼。
