# 提案编写常见陷阱与修复

编写面向决策层的技术提案时实际遇到的陷阱 + 修复。写完提案后逐条对照检查。

## 陷阱 1：叙事贬低既有工作

**症状**：用"翻转/降级/取代/旧 vs 新"叙事，把既有产品写成"被淘汰的旧东西"。

**为什么是问题**：既显得过去工作白做了（得罪既有团队），又让新工作显得高风险（像推翻重来）。

**修复**：改"延伸/拔高/新场景/建立在...之上"。用**双向增值**论点：既有工作因新能力延伸而更值钱；新能力因站在成熟底座上而低风险可行。

**例子**：
- ❌ "SQL 问数降为取数通道"
- ✅ "以 NL2SQL 问数为取数基础，向上构建"

## 陷阱 2：章节交织重复

**症状**：多个章节讲相关内容，用了**多套切分体系 + 多套命名**（如"编排层/编排大脑/主线编排"三个名字指同一物）；同一内容（如"底座"）在多个章节各讲一遍。

**为什么是问题**：读者以为是几套不同的东西在打架，读不懂、显得乱。

**修复**：
- 各章节各管一段（如：原则/架构/范围），职责不重叠
- 统一切分 + 统一命名（同一物一个名字）
- 不重复（某内容只在一个章节讲，其他章节引用）

**判据**：读者读到任何一段，都知道自己在决策链的哪一环。

## 陷阱 3：讨论过的重点无落点

**症状**：方案讨论/决策过的某个重点（某个模块、机制、约束），在最终提案里没有显式出现。

**为什么是问题**：领导会逐个检查"这个点落在哪了"——遗漏等于文档不完整，显得考虑不周。

**修复**：写完后自查——把讨论过的重点列出来，逐一在文档里找到落点。没找到的，补进去。

**例子**：G1 提案里沙箱、skills、意图分流、呈现层都是后来逐一补进主体路线的——每个都是用户检查后发现遗漏才补的。

## 陷阱 4：只有抽象原则，无落地锚点

**症状**：通篇讲设计理念/原则，但领导看不到"具体做什么、做到哪"。

**为什么是问题**：领导要判断"批不批、投多少"，需要具体的交付物和范围。纯抽象显得虚。

**修复**：
- 讲清主体路线（架构图 + 主流程）——骨架
- 给落地锚点（具名模块清单 + v1 做/不做边界）——具体交付
- 平衡"说骨架不说细节"，不是"什么都不说"

## 陷阱 5：缺本质差异论证

**症状**：只讲"用户要"（诉求层），没讲清"新工作和既有工作本质差在哪"。

**为什么是问题**：领导会问"为什么不能在现有产品里加几个功能？"——没有本质差异论证就回答不了。

**修复**：补"新工作 vs 既有工作"的本质差异表（如数据范围/过程/产出三个维度）。这些差异是方案各模块的根本理由。

## 陷阱 6：图乱 / 命名不一致

**症状**：ASCII 框图串行/错位；同一个概念在不同地方用不同名字。

**为什么是问题**：图乱显得不专业；命名不一让读者困惑。

**修复**：
- 图改 mermaid（+ subgraph 分组复杂架构）
- 节点标签避免特殊字符（`→` 用 `·` 替代）
- 全文统一命名（写完通读一遍，把同物多名统一）

## 陷阱 7：抽象产出写得太空

**症状**：写"输出洞察""支持决策"但不说具体洞察什么、决策什么。

**为什么是问题**：领导不知道这能力到底交付什么价值。

**修复**：给具体例子（如"主动提醒'这列缺失率异常'""找出跌幅最大的区域"），让抽象能力落地可见。

## 陷阱 8：提案里泄漏技术细节

**症状**：提案里出现 file:line、schema 定义、协议字段、代码结构等实施细节。

**为什么是问题**：领导读不懂、读不下去；也显得没分清"提案"和"设计"。

**修复**：把技术细节挪到设计文档，提案里用业务语言表达同一意思（如"数字由代码算"而非具体的函数签名）。

## 自检清单

写完提案后，逐条问自己：

- [ ] 叙事是"延伸/拔高"还是"翻转/降级"？（陷阱 1）
- [ ] 各章节是否各管一段、无重复？（陷阱 2）
- [ ] 同一概念是否全文同名？（陷阱 2、6）
- [ ] 讨论过的每个重点是否都有落点？（陷阱 3）
- [ ] 有没有架构图 + 主流程（主体路线）？（陷阱 4）
- [ ] 有没有具名模块 + v1 范围边界（落地锚点）？（陷阱 4）
- [ ] 有没有"新工作 vs 既有工作"本质差异论证？（陷阱 5）
- [ ] 图是不是 mermaid（非 ASCII）？（陷阱 6）
- [ ] 有没有技术细节泄漏（file:line/schema/协议字段）？（陷阱 8）
- [ ] 抽象能力有没有具体例子支撑？（陷阱 7）
