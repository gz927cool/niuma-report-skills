# gz 的提交信息写法

这个 skill 固化 git 提交信息的个人偏好，全部来自对真实提交的多轮返工。它防的是一类反复出现的返工：写的人把提交信息当"改动记录"逐条罗列改了什么，用户要的却是数月后重读时能立刻想起"为什么改"的总结——白话、短、有证据。违反任何一条大概率被打回。

## 核心观念：diff 自己会说话

打开提交的人能看到完整 diff。正文只写 diff 推不出来的东西：

- **动机**——为什么改，当时面对什么问题（放第一句，白话）
- **取舍**——几种做法里为什么选这种
- **验证证据**——只在携带新信息时写一句：验证对象+结论（等价性核验、契约校验类）；空泛的"测试全部通过"无新信息，不写
- **破坏性变更**及其理由

diff 一看便知的一律不写：机械步骤（"删 X 文件""改了调用方式"）、现状描述（"模型名只用 F1"）、字段/参数级枚举（"增 model_ver 与 infer_params.decimal_precision"）——**字段枚举是流水账的变体**，哪怕包装成"设计决策"罗列出来也是。

## 目标形态

**标题**：仓库历史已用 conventional commits（`type(scope): 中文一句话`）就沿用；scope 取模块/目录名，无明确模块可省。标题可承载能力级枚举（"删target暴露、多模型存储、三端点请求响应重构"——说的是能力不是字段操作）。

**正文（一句一行，通常 2-3 行，句间换行）**：

1. **动机行**：为什么改，凝练直述；要说现状就用"此前/原来"锚定，让读者一眼分清哪句是改动前、哪句是本次工作。可带 1 个核心锚点（如存储路径模板、关键数字），但不逐字段枚举。
2. **改动行**：以动词开头（新增/支持/为…添加…/改为/移除），一眼看出这是本次做的事；说用户可见的能力（"为同一来源添加时间窗口内尝试次数限制"），不写代码名与内部术语——不了解项目的读者也读得懂；细节留注释/文档。
3. **验证行（可选）**：只在携带新信息时写，写明验证对象+结论（"合并前后内容完全一致""样例 JSON 全部校验通过"）；空泛的"测试全部通过/全跑通"没有新信息，不写。

通俗 = 不用内部术语 + 直述机制，**不等于口语语气**——"顺手删掉""直接拒绝""逐个落盘""跑通"这类表达换成书面词。

写完自查方向是**"有没有废话"，不是"有没有漏说"**——逐行问"这条能从 diff 直接看出来吗？"能→删。

## 铁律

1. **绝不加任何尾注**：`Co-Authored-By`、`Generated with` 一律不加，用户多次明确要求。
2. **一次工作 = 一个总结式提交**：同一次会话的多个原子改动收进单个提交，正文做整体总结，不逐文件/逐提交罗列；已拆成多个时用 `git reset --soft` 合并后重提。
3. **只提交本次工作相关文件**：无关的工作区改动（其他 WIP、顺手改的配置）留在工作区，不裹挟进提交。
4. **用户要求改刚提交的信息 → `git commit --amend`**，不是追加新提交。

## 提交流程

1. `git status` + `git diff` 摸清本次工作的文件与范围，分清"本次工作"与"无关改动"。
2. 起草标题 + 一句一行的正文，对照自检清单删废话。
3. 提交。用户要求压缩/调整措辞 → `--amend` 重写，不追加新提交。

## 自检清单

- [ ] 逐行问：这条能从 diff 直接看出来吗？能→删
- [ ] 动机行用"此前/原来"锚定现状、改动行动词开头，读者分得清 before/after？
- [ ] 一句一行、句间换行，正文通常 2-3 行？
- [ ] 无代码名/内部术语，不了解项目的读者也读得懂？
- [ ] 验证行仅在携带新信息时出现（对象+结论），无空泛"测试通过"？
- [ ] 无口语语气（顺手/直接/跑通/落盘类）？
- [ ] 无任何尾注？
- [ ] 一次工作的多个原子改动合并为单个提交？
- [ ] 只含本次工作相关文件？
