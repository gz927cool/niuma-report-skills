# 面向领导的工作汇报（突出难点版）

写面向领导的工作汇报，核心只有一句话：**价值密度全在"难点"上，而难点是最容易写坏的。** 领导关心的不是"你执行了哪些操作"，而是"你解决了什么难问题、带来了什么价值"。

本技能用于周报、阶段报、专题汇报等需要把一段时期的技术工作讲透的场景。当日日报用 `gz-daily-work-log`，本技能专管"突出难点"的多日汇报。

## 总纲

一份合格的汇报，主线是"问题 → 决策 → 实施 → 效果"，不是任务清单。其中"难点"既是价值所在、也最容易踩坑。难点合格的唯一标准：

> **具体问题 + 为什么难，且只成立于这次的具体处境。**

下文所有规则，都是对这条标准的展开与防御。

## 总体结构：结果 → 行动 → 问题 → 规划

默认四段结构（用户另有指定时从其指定）：

- **结果**：先给结论。领导时间有限，先看到阶段成果，再决定是否细看过程。
- **行动**：主体，用 PDAR（见下）展开难点与攻坚。
- **问题**：**项目执行中遭遇的意外、阻塞、外部情境的复盘**。不是 PDAR 之 P，不是难点归纳！按"现象 → 根因 → 可验证 → 可改进 / 可复用"展开。
- **规划**：下一步要做什么。

### 关键：两种"问题"绝不能混

这是本技能最容易踩的坑——总体结构的"问题"段和 PDAR 的 Problem 都叫"问题"，但性质完全不同：

|  | PDAR 的 Problem | 总体结构的"问题"段 |
|---|---|---|
| 性质 | **主动要解决的目标**（业务痛点 / 技术挑战） | **被动遭遇的执行障碍 / 情境**（意外、阻塞、外部现状） |
| 语气 | 进攻性："存在 X 痛点，所以我们做 Y" | 反思性："我们撞上 X，根因 Y，下次 Z" |
| 来源 | 用户 / 业务需求、我们要攻克的技术挑战 | 项目过程中发现的非预期情境（环境约束、组织现状、外部变化） |
| 例子 | "用户问数需求边界扩散、查完又要分析、独立功能体验不连贯 → 必须引入主动路由保障 Agent 内部切换" | "实现呈现层时发现部门已有多种并存的集成方式、契约各不相同" |
| 服务目的 | 引出 Decision / Action / Result | 沉淀经验：可验证、可改进、可复用 |

同一件事可能两边都出现，但视角不同：PDAR 看"怎么把目标攻克"，"问题"段看"遭遇的意外为什么发生、下次怎么避免"。区分就一句话——**PDAR 之 P 是"我们要打的靶"，总体结构之问题段是"我们撞上的墙"**。

## 信息来源：先弄清"为什么"，再动笔

commit message 和任务清单只记录"做了什么（what）"，不记录"为什么做（why）"。动笔前先回到原始材料补全意图：查对话记录、设计文档、决策记录，弄清每个动作到底是"修复 bug""响应需求变更"还是"主动架构优化"——这决定了汇报的叙事角度。凭 commit message 猜动机，是误判的主要来源。

## 难点表述的六种毛病（写作时自检、审稿时排查）

难点是最容易写坏的。写难点时对照下表逐条自检，任何一条不过就改：

| 毛病 | 典型表现 | 自检问句 |
|---|---|---|
| **套话** | 放哪个项目都成立（"没有现成判据可抄"） | 换成别的项目还成立吗？成立 → 删或改实。 |
| **情绪渲染** | 只喊难、看不出遇到什么（"靠拍脑袋收不了场"） | 能说出具体遇到什么问题吗？ |
| **防御性表态** | 声明"这是真问题"（"是真权衡而非口水仗"） | 删掉这句定性，硬伤还在吗？在，就多余。 |
| **选择题式** | 光摆选项不亮代价（"该自动还是显式"） | 读者会想"那选 X 呗"吗？会，就是没说为什么难。 |
| **一刀切笼统** | 把正交维度压扁（"管紧还是放开"） | 这里的"难"其实是几个独立问题？分开写。 |
| **错位** | 把表象/结果/被规避的当难点（"AI 编数"、被推迟的功能） | 这是"为什么难"，还是"发生了什么"？是本阶段真攻克的，还是被绕开留到后面的？ |

记住：真问题不需要声明自己是真问题；直接把硬伤亮出来，读者自然知道它是真难点。

### 五类"真正的难点本质"

写难点要落到工程本质，不要停在表象（"X 不工作""模型会编数"都是表象，要去问"为什么这难做"）。真正的难点通常属于以下五类之一，写时对号入座：

- **艰难权衡**：两难、无完美解，必须取舍（如 SQL 全量精确 vs Python 灵活采样，各有硬伤）。
- **外部硬约束**：平台 / 协议 / 安全 / 第三方宿主的不妥协限制（如开发平台让隔离技术全失效、宿主安全策略默认拒绝）。
- **反复返工**：同一问题经历多版方案才解决（如呈现层四次更迭、某开关三轮反复）。
- **跨层不匹配**：根因不在出错的那一层（如超时报在客户端、根因在长输出 + 重试策略；本地全绿、生产才炸）。
- **需发明新判据**：没有现成范式，要把开放争论变成可验证约束（如"新增一类分析不该触动编排层"）。

## PDAR：把行动展开成 Problem → Decision → Action → Result

行动是汇报主体。当工作有明确的技术难点时，按 PDAR 展开，而不是平铺成果。各层各司其职——**尤其不要把下一层的内容混进上一层**：

- **Problem（难在哪）**：**行动要解决的目标问题**——一个业务痛点或技术挑战，引出"我们要做什么"。薄、汇总。**绝不混入 Decision / Action 的 solution**（"怎么解决"留给后面）——P 一旦带出方案，就会和 D/A 重复，P 也失去"点出靶子"的定位。
- **Decision（分析与决策）**：怎么定的、为什么这么定。如实呈现反复与转折（试过 A → 撞墙 → 改 B），这才是难度所在；不要写得像一步到位。
- **Action（具体实施）**：具体做了什么动作。
- **Result（结果）**：取得了什么效果，能量化则量化。

注意：这里的 Problem 是"我们主动要打的目标"，和总体结构"问题"段的"遭遇的墙"是两回事（见上面的对比表）。

## “问题”段怎么写：用复盘体现成长

总体结构的"问题"段是复盘，不是难点归纳。目的是让领导看到你**从事儿里学到了什么、下次能做得更好**——成长性是通过复盘的实质体现的，不是靠声明"我在反思"。

**思考骨架（写给自己，不进正文）**：每条复盘确保这四样都有——遭遇的现象、根因、可验证的证据、可改进且可复用的教训。这是动笔前的内部检查清单，保证反思到位。

**但绝不把这四样当标签写进报告**（"现象：…… 根因：…… 可验证：…… 可复用：……"）。那是填表，不是复盘。要把四要素融成一段自然语言，让根因、证据、改进自然流露。

❌ **归纳式（错）**："跨环境正确性是最隐蔽的高危难点……"——讲道理，不是复盘。
❌ **标签填表式（也错）**："现象：本地全绿生产报错。根因：……。可验证：……。可复用：……"——把骨架当格式，机械，像在声明"我在反思"。
✅ **复盘式（对）**："画像联调时本地全绿、上生产却返回空且不报错，排查才发现系统在静默降级：本地库返回元组、生产返回列表，解析层只认元组于是悄悄丢弃，本地永远测不出。我们据此把解析环节改为统一返回结构化数据、要求失败显式报错，并补了结构化适配测试确认修复生效。这条此后成了检查项——凡'本地绿、生产红且静默'都是同一模式，跨环境项目该用生产同构数据建测试链路。"

四要素都在（现象 / 根因 / 可验证 / 可复用），但没有一个标签。

## 结构与取舍

- **正交维度分开写**：两个独立的问题不要揉成一句。如"指令怎么组织"和"工具怎么设计"是两件事，各占一条，不要压成"管紧还是放开"一刀切——那会把结构写丢。
- **诚实区分"真攻克 vs 被规避 / 推迟"**：被绕开、推迟的工作放"规划"，不当成本阶段难点或成果。
- **问题驱动，不是成果罗列**：主线是"解决什么难问题、怎么破的"，不是"做了哪些事"。逐条翻译 commit message 是反模式。
- **编写思路不进正文**：报告只呈现"写了什么"，不呈现"我是怎么写的"。"这一节按 X 结构展开""下面分 N 点"这类自我说明、"现象：/ 根因：/ 可验证："这类编写骨架，都是给写作者看的脚手架，一律不进正文——领导要的是结构本身，不是对结构的解释。

## 语言

- **第一人称**：这是你给领导的汇报，不是 AI 助手的执行记录。全文不出现"用户""指示""响应""按照要求"等 AI 交互痕迹；如果你借助了 AI 助手，直接写"我做了什么"。
- **业务语言为主**：用"匹配维度扩展"不说"消除 if/elif 链"。
- **保留关键技术概念**：沙箱、内容安全策略（CSP）、协议契约、库内下推……这些能体现技术含量，保留，必要时配一句通俗解释。
- **绝不出现实现细节**：函数名、变量名、文件路径、端口号、命令、URL 一律不出现。领导不关心这些。
- **不引述代码**：用一段自然语言能说清的事，不要贴代码片段。
- **共享基线**：作者口吻（第一人称、无 AI 交互痕迹）与格式基线由 `../gz-shared/core/report-baseline.md` 统一约束。

## 反面教材（这些写法都要改）

❌ **套话**："SQL/Python 路由——没有现成判据可抄"
✅ "SQL/Python 路由——两条路不可兼得、各有硬伤，而且错不起：判据定错的代价不对称，该用 Python 的塞进 SQL 能力被阉割，本可全量的却走采样等于把近似当精确交付"

❌ **情绪渲染**："架构判据——每种选择都有硬伤，靠拍脑袋收不了场"
✅ "分析能力该怎么组织——做成固定工具会僵化、全交给模型会失控，这道分界划在哪都有代价"

❌ **Problem 混入 solution**："难点是流程分层……落点是三层职责分离：把系统提示瘦身为路由指引、技能分主控/方法/参考三层"
✅ Problem 只留目标问题；方案（三层职责分离等）移到 Decision

❌ **把表象当难点**："难点是 AI 会编数"
✅ 下沉到本质："难点是让数字脱离模型之手，而保证机制本身还会被更深的 bug 绕穿"

❌ **把"问题"段写成难点归纳**："可信度是契约不是口号""跨环境正确性最隐蔽"——这是讲道理，不是复盘
✅ 写成融含四要素的自然段（形态见上文复盘式示例）
