# 从对话记录补全 commit 意图

> 条件加载：仅当 commit message 无法可靠判断工作动机时使用本模块；正常情况下无需加载。


**git commit message 通常只记录做了什么（what），不记录为什么做（why）。** 在以下情况下，必须查阅当日对话记录来补全意图：

- commit message 使用了泛化动词（"重构""修复""优化"）但未说明解决什么具体问题
- 多个提交涉及同一模块，但无法从 message 判断它们之间的关系
- commit message 描述的行为与直觉相反（如"请求传入的 model 不再生效"——这是 bug 修复还是需求变更？）
- 一个提交改动多个模块，看不出主线逻辑

**查阅方法**：

1. 列出今日对话记录（文件名时间戳是 UTC，本地时间 = UTC + 8；本地零点到八点的会话盖的是昨日 UTC 戳，两个前缀都要列）：
   ```bash
   ls .specstory/history/$(date +%Y-%m-%d)*.md .specstory/history/$(date -d "yesterday" +%Y-%m-%d)*.md
   ```

2. 读取对话文件开头，按时间顺序理解当日的完整工作链条：
   - 用户发起了哪些请求？按时间顺序读，不要跳过。
   - 用户反馈了什么问题？（测试报错、系统异常、行为不符合预期）
   - 哪些问题是 Claude Code 在对话中即时修复的，哪些被记录为 commit？
   - 用户是否明确表达了需求变更（"根据需求变更""现在必须使""要求改为"）？

3. 将对话上下文与 git commit 交叉对照：
   - 如果 commit 是对某个用户报告的修复 → 日志应写"测试中发现 XX 问题，根因为 YY"
   - 如果 commit 是需求变更 → 日志应写"响应需求变更，将 XX 改为 YY"
   - 如果 commit 是主动架构优化 → 日志应写"针对之前遇到的 ZZ 痛点，进行了架构调整"
   - 如果同一个问题经历多轮对话才解决 → 合并为一个问题域

4. **关键判断**：每个 commit 的动机是"修复 bug""响应需求变更"还是"主动优化"？这决定了工作日志的叙事角度。

**重要**：如果当日对话记录不存在（`.specstory/history/` 下无今日文件），跳过此步，仅基于 git log 编写。
