# 工作日志撰写

将当日 git 提交记录转化为面向领导的自然语言工作汇报。

## 核心原则

**问题驱动，而非任务罗列。** 领导关心的是"你解决了什么问题、带来了什么价值"，不是"你执行了哪些操作"。

## 四步转化法

### 第 1 步：从 git log 提取事实

```bash
git log --since="today" --format="%h %s"
git diff --stat HEAD~N..HEAD
```

记下：今天做了哪些提交、涉及哪些模块、有没有新增文件/功能。同时检查是否有未提交的工作产出（文档、设计、调研、会议记录等）。

### 第 1.5 步：从对话记录补全意图

当 commit message 无法可靠判断工作动机时（泛化动词未说明具体问题、同一模块多个提交关系不明、行为与直觉相反、一个提交跨多模块看不出主线），按 `references/conversation-intent.md` 的流程从当日对话记录补全意图；正常情况下无需加载该模块。

### 第 2 步：将提交归类为"问题→解决→效果"

把每个提交映射到三个问题：
- **它解决了什么业务问题或技术痛点？**（用第 1.5 步补全的意图来回答，不是翻译 commit message）
- **怎么解决的？**（一句话概括方案，不展开技术细节）
- **取得了什么效果？**（可量化则量化，否则说清改善了什么）

多个相关提交合并为一个问题域，不要逐个提交罗列。如果多个提交都是同一个测试-修复循环的结果，应合并为一段。

### 第 3 步：用自然语言写成段落

以"背景问题→今日完成→取得效果"的结构组织成三个加粗标题段落。语言要求：
- 所有今日工作内容归入"今日完成"段落，不要拆分出"线上问题修复""可观测性修复"等额外加粗标题
- "今日完成"内部可以有多个自然段落，主题之间用句号分隔，不额外使用小标题
- 像给同事口头汇报一样写，不要像写 commit message
- 用业务语言而非技术语言（说"匹配维度扩展"不说"消除 if/elif 链"）
- 不要出现代码片段、函数名、文件名、环境变量名、端口号、URL 等实现细节。领导不关心这些，只关心问题是什么、怎么解决的、效果如何。用一段自然语言说清的事，不要引述代码
- 每段一个主题，段落间有逻辑关联
- 始终以**你的第一人称口吻**撰写——这是你给领导写的工作汇报，不是 AI 助手的执行记录。全文不应出现"用户""指示""响应""按照要求""根据用户反馈"等 AI-用户交互痕迹。如果你通过 AI 助手完成了工作，直接写你做了什么即可，不提 AI 的存在
- 如果对话记录揭示了完整的工作背景（如"昨天测试不通过，今天继续修复"），要在开头段落交代承上启下的背景

## 反面案例

❌ **罗列提交**：
> - 84112f5 refactor: dimensions 配置驱动匹配引擎
> - e12f334 refactor: EnterpriseRepo 通用条件接口
> - 1440af8 fix: EnterpriseRepo 表名由配置驱动

❌ **任务清单式**：
> 1. 匹配引擎审计
> 2. 引擎重构
> 3. 新增场景
> 4. 文档更新

❌ **代码细节堆砌**：（面向领导的汇报不应出现代码级细节）
> 将 `_non_stream_openai_response` 改为 async 函数，使用 `loop.run_in_executor` 将 `graph.invoke()` 放到独立线程池，修复了回调 `localhost:8000/mcp/messages` 时的超时问题…

实际上这句话应该写成：
> 修复了非流式调用链路的异步死锁问题——根因是事件循环被长时间阻塞，导致下游工具内部通信永久等待。修复方案是将非流式路径与流式路径对齐，统一将核心任务放入独立线程池执行。

函数名、变量名、URL、端口号、代码片段一律不出现在日志中。

❌ **技术细节堆砌**：
> 将 `_score_candidate()` 中 5 个硬编码 `if/elif` 分支改为配置驱动循环，将 `EnterpriseRepo.find_candidates()` 的 5 个命名参数改为 `conditions: dict[str, list[str]]` 通用接口...

❌ **AI 助手口吻**：（撰写人应以自己的第一视角写，不应以 AI 助手的口吻）
> 响应用户继续修复直至 MCP 服务正常可用的指示，对工具层进行了重构…

实际上这句话应该写成：
> 继续推进昨日未完成的 MCP 服务联调修复工作，对工具层进行了重构…

**日志是你的工作汇报，不是 AI 助手的执行记录。** 全文不应出现"用户""指示""响应""按照要求"等 AI 与用户交互的痕迹。

❌ **误判动机**：（未查阅对话记录导致的典型错误）
> 修复了请求传入的 model 参数失效的 bug…

实际上对话记录显示是需求变更："根据需求变更，现在必须使得请求传入的model无效"——这不是 bug 修复，而是有意的设计调整。

## 正面案例

✅ **问题驱动 + 自然语言 + 效果导向**：
> **背景问题**：匹配引擎在代码中硬编码了大量维度分支和数据库字段白名单，新增一个匹配维度必须改动多处引擎代码，难以通过配置文件的扩展意图，无法快速适配更多业务场景。
>
> **今日完成**：1.对匹配接口全链路进行审计，定位硬编码根因并完成去硬编码改造。重构后新增匹配维度只需在 JSON 中声明即可，引擎自动适配；2.基于新架构新增了一个匹配场景，从零配置到可运行仅需一个 JSON 文件；3.同步更新了相关文档。
>
> **取得效果**：匹配维度扩展从"改代码 + 测试回归"简化为"新增一个 JSON 配置文件"，可扩展性显著提升，新匹配场景已可用。

## 常见错误

| 错误 | 正确做法 |
|------|---------|
| 逐条翻译 git commit message | 合并相关提交，按问题域归类 |
| 不查对话记录，凭 commit message 猜测意图 | 先用第 1.5 步查对话记录，再归类 |
| 使用技术术语（refactor、硬编码、if/elif） | 用业务语言（架构优化、配置驱动、自动适配） |
| 罗列文件清单或代码行数 | 说清改了什么模块、为什么改 |
| 写成流水账（上午做A下午做B） | 按"问题→解决→效果"组织 |
| 堆砌细节让领导自己总结 | 你替领导提炼关键信息 |
| 把需求变更写成 bug 修复 | 查对话记录，确认原始动机 |
| 把多次迭代修复写成孤立事件 | 合并为同一个问题域的"发现→诊断→修复"链条 |
| 使用 AI 助手口吻（"响应用户指示""按照要求"） | 以自己的第一人称写，不提 AI 的存在 |
| 出现函数名、变量名、URL、端口号 | 用自然语言描述问题和方法，去掉所有代码引用 |

## 特殊场景处理

当日无提交、跨多日、当日工作较少、无对话记录可用等非典型场景，按 `references/special-cases.md` 处理；仅在命中对应场景时加载该模块。

## 产出要求

- 篇幅：通常 3-5 段，总计 200-400 字
- 格式：Markdown，一级标题为"工作日志 — 日期"；格式基线与作者口吻由 `../gz-shared/core/report-baseline.md` 统一约束
- 落款：不需要署名和日期（OA 系统自带）
- 写入位置：`docs/work-log/YYYY-MM-DD-工作日志.md`（项目级）或由用户指定
